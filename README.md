# Динамические лимиты в каскаде ранжирования + A/B-анализ

Проект для подготовки к собеседованию в Группу операций машинного обучения Яндекса.

В каскаде из двух стадий (дешёвая → дорогая) фиксированный лимит K либо тратит
вычисления на простых запросах, либо режет качество на сложных. Я обучил модель
лимитов на признаках дешёвой стадии, которая предсказывает K для каждого запроса.
На публичном датасете MSLR-WEB10K (использована встроенная подвыборка catboost.datasets.msrank_10k() для скорости итераций) динамический лимит **доминирует fixed-K по Парето**:

- При незначимом изменении NDCG@10: **−0.0093** (95% ДИ: [−0.0289, +0.0064])
  число вызовов дорогой модели снизилось на **19.4%** (95% ДИ: [−26.6%, −11.2%]).
- По сравнению с Fixed K=50: экономия **−19%** стоимости при потере **−0.009** NDCG@10.
- Pareto gain: **+0.0152** NDCG@10 при той же стоимости (точка выше кривой fixed-K).

Процедура оценки прошла A/A-тест (FP rate 4.5% для NDCG, 2.0% для cost).
MDE-анализ: при n=35 парный дизайн видит только падения NDCG ≥ 0.026; для детекции
эффекта 0.009 в реальном A/B нужно ~20 000 запросов — что подчёркивает ценность
парного дизайна в офлайн-анализе.

---

## 1. Постановка задачи

Каскадное ранжирование — стандартная архитектура в поиске и рекламе:

- **Дешёвая стадия** (лёгкая модель, мало признаков, быстро) — грубо фильтрует
  кандидатов, оставляет top-K.
- **Дорогая стадия** (тяжёлая модель, все признаки, медленно) — точно
  переранжирует этих K документов.

**Проблема:** чему равен K? Фиксированный K — плохой компромисс:

- K слишком маленький → на сложном запросе хороший документ не попадает в top-K
  дешёвой модели → дорогая его уже не увидит → качество падает.
- K слишком большой → на простом запросе гоняем дорогую модель на 50 документах,
  хотя хватило бы 10 → тратим вычисления зря.

**Цель:** предсказать K под каждый запрос по сигналам, известным **после дешёвой
стадии и до вызова дорогой**. Ошибка в сторону переоценки K дешевле, чем в сторону
недооценки — это реализуется через асимметрию функции потерь.

---

## 2. Данные

**Датасет:** MSLR-WEB10K (Microsoft Learning to Rank), загружен через
`catboost.datasets.msrank_10k()` — 20 000 запросов суммарно во встроенных
train/test. 136 признаков, метки релевантности 0–4.

**Очистка:**
- Удалены **3 запроса** без релевантных документов (все метки = 0), это ~1.7%
  от 175. Причина: NDCG для таких запросов не определена (IDCG = 0), включение
  их с NDCG=0 искусственно занижало бы метрику.
- Итог: **172 запросов**, средний размер ~120 документов.

**Разбиение (строго по `query_id`, не по строкам):**
- **A** (обучение каскада): 103 запроса.
- **B** (обучение модели лимитов): 34 запросов.
- **C** (финальная оценка и A/B): 35 запросов.

Почему три части, а не две: если обучать модель лимитов на тех же запросах, где
обучались ранкеры каскада, таргет K будет искажён — модели «знают» эти запросы,
и минимальный K окажется нереалистично маленьким.

## 3. Методология

### 3.1 Каскад

**Дешёвая модель:** LightGBM `lambdarank`, 30 из 136 признаков, 80 деревьев,
глубина 5.

**Дорогая модель:** CatBoost `YetiRank`, все 136 признаков, 300 итераций,
глубина 7.

**Стоимость (условные единицы, у.е.):**
- дешёвая стадия: 1 у.е. / документ;
- дорогая стадия: 10 у.е. / документ;
- стоимость запроса: `n_docs * 1 + min(K, n_docs) * 10`.

Соотношение 1:10 выбрано как порядок величины разницы (30 vs 136 признаков,
LightGBM vs CatBoost). В реальной системе берётся из профилирования latency;
в проекте — фиксированное, важно именно **отношение**.

**NDCG@10 для каскада:** документы вне top-K получают `-inf` и не дают вклада
в DCG. Это стандартный подход в cascade ranking (Wang et al., SIGIR 2011) —
иначе NDCG при K<10 считается неправильно (неотскоренные документы случайно
могут попасть в top-10 и завысить метрику).

**Fixed-K baseline:** перебор K ∈ {5, 10, 20, 50, 100, 200, 230} на части C.

| K | NDCG@10 | Cost |
|---|---|---|
| 5 | 0.2583 | 160.1 |
| 10 | 0.3736 | 208.6 |
| 20 | 0.4050 | 305.2 |
| 50 | 0.4654 | 584.6 |
| 100 | 0.4710 | 968.9 |
| 200 | 0.4720 | 1188.3 |
| 230 | 0.4720 | 1205.5 |

Кривая выпуклая: от K=5 к K=20 NDCG растёт быстро, от K=50 к K=230 — почти
плато. После K=50 дополнительные вычисления не окупаются.

### 3.2 Таргет K и модель лимитов

**Таргет K:** для каждого запроса из B находим минимальный K, при котором
`NDCG_full − NDCG_K <= ε`, где `NDCG_full` — полный прогон дорогой модели.
Использованы три ε ∈ {0, 0.01, 0.02} — разный компромисс качество/стоимость.

**Оптимизация:** дорогая модель прогоняется **один раз** на всех документах
запроса, скоры для top-K берутся из этого же прогона (GBDT не контекстная).
Это в 7 раз меньше вызовов дорогой модели — та же оптимизация, которую мы
делаем в реальной системе.

**Признаки модели лимитов — 41 штука, только из дешёвой стадии:**
- о запросе: `n_docs`, `log_n_docs`;
- о скорах дешёвой: max, min, std, mean;
- разрывы: 1-2, 1-5, 1-10, 1-20;
- энтропия нормированных скоров;
- агрегаты (mean/std/max) top-10 **важных** признаков дешёвой модели по top-10
  документам.

**Модель:** LightGBM `quantile regression` на `log(K+1)`, `alpha` — целевой
квантиль. `alpha > 0.5` сдвигает предсказания вверх = запас на асимметрию
потерь («переоценить K дешевле, чем недооценить»). Округление вверх до
ближайшего K из сетки через `searchsorted`.

**Sweep по `eps × alpha`** (15 конфигураций): нашли конфигурации, где модель
не «схлопывается» к одному K и даёт точку **выше** кривой fixed-K.

**Финальная конфигурация:** `eps=0.01, alpha=0.8`.

### 3.3 A/B-симуляция

**Контроль:** Fixed K=50 (ближайший по стоимости к dynamic).
**Тест:** Dynamic K с финальной конфигурацией.

**Парный vs групповой дизайн:**
- **Парный:** каждый запрос C оценивается в обоих вариантах, считаем разницу
  `Δ_i = NDCG_test_i − NDCG_control_i` по каждому запросу. В офлайне это
  возможно и даёт более узкие ДИ, потому что устраняет межзапросную дисперсию.
- **Групповой:** случайно делим C на две половины, каждая видит только один
  вариант. Симулирует реальный A/B, даёт широкие ДИ.

**Доверительные интервалы:** перцентильный bootstrap по **запросам** (5000
ресемплов), не по документам — документы внутри запроса коррелированы, ресемпл
по документам занижает дисперсию.

**A/A-тест:** 200 случайных разбиений, обе группы с Fixed K=50. Доля ложных
срабатываний должна быть ≈ 5% при α=0.05.

**MDE (минимальный детектируемый эффект):** `(z_{1−α/2} + z_{1−β}) · SE`
при мощности 80%, α=0.05.

## 4. Результаты

### 4.1 Финальная конфигурация

`eps=0.01, alpha=0.8`. Модель предсказывает K=30 для 77% запросов C,
K=50–100 для остальных 23%:

### 4.2 Динамический K vs Fixed K=50

| Метрика | Fixed K=50 | Dynamic | Δ (95% ДИ, bootstrap) |
|---|---|---|---|
| NDCG@10 | 0.4654 | 0.4561 | **−0.0093** [−0.0289, +0.0064] |
| Cost | 584.6 | 473.8 | **−110.9** [−158.6, −54.6] |
| Cost% | — | — | **−19.4%** [−26.6%, −11.2%] |

**Интерпретация:**
- Δ NDCG ДИ **включает 0** → значимого падения качества не детектируется.
- Δ Cost% ДИ **полностью ниже 0** → экономия статистически значима.

### 4.3 Pareto gain

При той же стоимости, что dynamic (473.8), интерполированный fixed-K дал бы
NDCG = 0.4410. Dynamic даёт 0.4561. **Pareto gain: +0.0152 NDCG** при той же
стоимости — точка лежит выше кривой fixed-K.

### 4.4 Парный vs групповой дизайн

| Метрика | Парный ДИ (ширина) | Групповой ДИ (ширина) | Отношение |
|---|---|---|---|
| Δ NDCG | 0.0352 | 0.2977 | **8.5x шире** |
| Δ Cost | 104.0 | 250.1 | **2.4x шире** |

Парный дизайн использует **внутризапросную** дисперсию (std(Δ_i) ≈ 0.05),
групповой — **межзапросную** (std(NDCG) ≈ 0.18). Отсюда разница в 3.6x по std
и 8.5x по ширине ДИ для NDCG.

### 4.5 A/A-тест (проверка процедуры)

| Метрика | Bootstrap FP rate | t-интервал FP rate | Ожидание |
|---|---|---|---|
| NDCG | 5.5% | 4.5% | 5% |
| Cost | 9.5% | 2.0% | 5% |

Bootstrap **под-покрывал** cost (FP rate 9.5% > 5%) из-за правосторонней
скошенности распределения (длинный хвост запросов с большим `n_docs`).
t-интервал (Welch) даёт номинальные 5% для NDCG и консервативные 2% для cost.
Основной вывод устойчив к выбору метода CI.

### 4.6 MDE (минимальный детектируемый эффект)

| Метрика | MDE при n=35 | Наблюдаемый эффект | Вердикт | Нужно n |
|---|---|---|---|---|
| NDCG (парный) | 0.0258 | −0.0093 | НЕ видим | ~273 |
| NDCG (групповой) | 0.2245 | −0.0093 | НЕ видим | ~19 843 |
| Cost% (парный) | 11.50% | −19.42% | **ВИДИМ** | ~4 |

Для детекции падения NDCG на 0.009 в реальном A/B нужно **~20 000 запросов
на группу** — это подчёркивает ценность парного дизайна в офлайн-анализе.
Экономия cost 19% значительно превышает MDE парного дизайна (11.5%) — поэтому
детектируется даже на 35 запросах.

## 5. Ограничения

### 5.1 Ограничения данных

- **Мало данных в B:** 35 запросов — этого недостаточно для стабильного
  обучения GBDT-модели на 41 признаке. `trees=1` в 7 из 15 конфигураций sweep
  — модель останавливается почти сразу на early stopping из-за малого
  валидационного набора (6–7 запросов). На реальных данных с 5000+ запросов
  в B модель предсказывала бы лучше.
- **Мало данных в C:** 35 запросов в C — это **1/3** от полного MSLR.
  Групповой A/B на 35 запросах ничего не видит, и это ожидаемо. MDE-анализ
  показывает: для детекции эффекта 0.009 нужно ~20 000 запросов.
- **NDCG@10 шумный:** на одном запросе метрика нестабильна; при малом числе
  релевантных документов потеря 0.01 может быть следствием перестановки двух
  документов, а не реальной деградации.

### 5.2 Методологические ограничения

- **Офлайн ≠ онлайн:** нет обратной связи, нет смещения выбора (position
  bias), нет эффектов задержки, разная нагрузка в разное время. В офлайне
  каждый запрос оценивается в обоих вариантах — это идеализация.
- **Нет бизнес-метрики:** в проекте качество измеряется через NDCG,
  стоимости — в условных единицах. В реальной рекламе есть аукцион, деньги,
  ROI — эти метрики отсутствуют.
- **Не рекламные данные:** MSLR-WEB10K — поисковый датасет. Структура задачи
  (запрос → кандидаты → дешёвая стадия → дорогая стадия) та же, но бизнес-
  контекст другой.
- **Таргет зависит от выбранной дешёвой модели:** если переобучить дешёвую
  модель, модель лимитов нужно переобучать тоже — её признаки меняются.
- **Модель лимитов зависит от α:** в финальной конфигурации `under=23%`
  (на 23% запросов предсказали K меньше идеального). Это осознанный компромисс
  ради экономии: `pareto_gain` остаётся положительным.

### 5.3 Статистические ограничения

- **Bootstrap под-покрывает скошенные метрики при малом n:** FP rate 9.5% для
  cost в A/A при n=17–18. Решение: для A/A использовать t-интервал Welch —
  он консервативнее и номинально корректен. Основной вывод (значимая
  экономия) устойчив к выбору метода.
- **Парность недоступна в реальном A/B:** в проде каждый запрос видит только
  один вариант. Поэтому в реальном A/B нужны тысячи запросов для детекции
  малых эффектов.

## 6. Трудности и как их решили

**Проблема:** A/A-тест дал FP rate 9.5% для cost (ожидание 5%).

**Причина:** percentile bootstrap **под-покрывает** скошенные распределения
при малом n. Cost имеет длинный правый хвост (несколько запросов по 200+
документов дают cost ~2500 при медиане ~550). При n=17–18 bootstrap-ресемпл
может случайно не содержать «выброс» и дать слишком узкий ДИ.

**Решение:** для A/A использовать t-интервал Welch — консервативнее и
номинально корректен. Сохранили оба результата (bootstrap 9.5% / t 2.0%) как
свидетельство, что проверили ограничение, а не «подогнали» метод.

## 9. Как проект связан с командой

| Команда | Проект |
|---|---|
| Прогнозировать оптимальные лимиты на стадиях подбора | Модель предсказывает K — сколько кандидатов отдать в дорогую стадию |
| Балансировать качество и вычислительные затраты | Парето-кривая: NDCG@10 vs cost, динамический K доминирует fixed-K |
| Наращивать прибыль без роста железа | −19% стоимости при незначимом падении качества |
| Определять, стоит ли участвовать в аукционе | Та же логика: предсказать ценность запроса по дешёвым сигналам до дорогих вычислений |
| Полный цикл гипотеза → данные → эксперимент | Разбиение A/B/C, Парето, A/B-симуляция, bootstrap, A/A, MDE |

**Ключевая идея:** динамический лимит — это решение **до** дорогих вычислений
по дешёвым сигналам. В проекте оно применено к выбору K; в команде — к лимитам
на стадиях подбора и к решению об аукционе. Логика одна: **предсказать
ценность запроса заранее и не тратить ресурсы там, где не окупится**.
